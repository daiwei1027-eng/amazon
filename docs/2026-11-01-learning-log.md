## 二、全量数据整理与 Parquet 保存

### 日期转换与排序

新增 `convert_sales_date()`，检查 `date` 列是否存在，以及类型是否为 `pl.String` 或 `pl.Date`。字符串日期按 `%Y-%m-%d` 严格解析；已经为日期类型时保留，再统一检查行数、销量总和、日期空值和结果类型。

这里需要区分三个对象：

| 写法 | 含义 |
| --- | --- |
| `sales["date"]` | 一整列数据，类型为 Series |
| `sales.schema.get("date")` | 该列的 Polars 数据类型 |
| `pl.col("date")` | 用于处理该列的表达式 |

列类型使用 `pl.String`、`pl.Date` 判断，不能通过 `type(整列) == str` 判断。日期转换表达式放在 `with_columns()` 中执行，并接收返回的新表。

最终按 `store_id`、`item_id`、`date` 排序，使同一门店商品的历史按时间排列。后续滞后与滚动计算仍需要明确按销售序列分组。

销量空值与日期转换是不同的约定。本函数检查转换前后销量总和保持不变，不额外拒绝原本可能存在的销量空值。测试覆盖 `[3, None]` 的总和保留情况；本次实际 M5 文件中的销量空值数为零。

### 文件路径与持久化

输出目录配置为 `processed`，相对于配置中的 `data` 目录；文件名只保存名称。组合顺序为项目根目录、数据目录、输出目录、文件名。

不能先将文件名与数据目录拼成绝对路径，再与输出目录组合：`Path / 绝对路径` 会采用右侧绝对路径，从而忽略前面的目录。

创建目录使用 `mkdir(parents=True, exist_ok=True)`；该方法返回 `None`，不使用 `with`。写入时在 DataFrame 对象上直接调用 `write_parquet()`。保存后读回，检查形状、完整 schema、销量总和与价格空值数量。

## 三、小样本实验范围与可复现抽样

### 为什么保存全量文件，却使用子集训练

全量清洗产物与正式实验规模是两个独立选择。保存完整处理结果，使下游可以复用相同数据入口；训练采用固定子集，控制本地资源占用和反复实验成本。

本机配置已核实为 i7-12700KF、约 32 GB 内存、RTX 5060 8 GB 显存。全量长表约 5,918 万行，后续特征、中间副本、窗口构造和模型训练会增加资源开销。正式实验选择小样本，重点验证处理规则、时间划分、模型比较与结果解释；当前没有用训练实测证明全量训练不可行。

已在 README 中补充实验规模选择依据。该说明还需要随实际进度更新，其中最初写的“正式样本范围尚待确定”目前已经有了明确结果。

### 采样参数与职责

`inspect_m5.py` 负责完整清洗产物；`inspect_m5_scope.py` 读取该产物，调用 `sample_sales()` 并保存独立子集。纯采样函数不读取 YAML、不访问 MinIO，也不写文件。

本次参数为：

```yaml
sampling:
  item_counts: 100
  store_ids: ["CA_1", "CA_2"]
  seed: 42
```

该配置实际位于 `data.sampling` 下。门店数量通过 `len(store_ids)` 计算，避免门店列表与另一个数量参数不一致。

### 抽样步骤

1. 从日销量长表选择 `store_id`、`item_id`、`cat_id` 并去重，得到门店商品元数据。
2. 筛选配置指定的两个门店，得到 6,098 个门店商品组合。
3. 按 `item_id` 分组，聚合不同门店数量，保留数量等于目标门店数的商品，得到 3,049 个共同商品。
4. 将共同商品按 `item_id` 排序，再使用 `sample(n=100, seed=42)` 抽取商品。
5. 回到完整日销量表，按目标门店和抽中的商品清单筛选，保留全部日期与字段。

聚合在这里的含义是“每个商品出现在几个不同门店”，使用 `n_unique()` 统计门店数量。不能将长表每天的重复记录当作不同商品，也不能直接随机抽取日记录，否则会破坏销售序列的历史完整性。

固定种子之外，还要先固定候选列表顺序：分组与去重默认不保证输出顺序。当前抽样重现已在实际数据上核对，结果与配置种子一致；跨库版本的抽样行为仍应结合版本和保存的商品清单确认。

## 四、Docker Compose 与 MinIO

### 已实际运行的服务

当前 Compose 仅定义并运行 MinIO。MLflow、Airflow、TorchServe、FastAPI 已规划客户端连接端口，尚未在本项目 Compose 中部署。

MinIO 使用固定版本镜像：

```text
ghcr.io/coollabsio/minio:RELEASE.2025-10-15T17-29-55Z
```

这是 Coollabs 根据 MinIO 官方源码构建的第三方镜像，构建来源见 [Coollabs MinIO 仓库](https://github.com/coollabsio/minio)。本次核验了版本清单包含本机所需的 `linux/amd64`。MinIO 社区上游已归档且采用源码分发，旧教程中的官方历史镜像标签在本次查询中无法获取，因此记录实际可用的发布来源与固定版本。

本机原有的 `rag-agent:local` 镜像保留，未因新项目清理或删除。现有 Docker Engine 网络配置也没有由助手修改。

### 配置含义

| 配置 | 当前含义 |
| --- | --- |
| `services.minio` | 定义名为 minio 的容器服务 |
| `image` | 指定程序镜像与版本 |
| `command` | `server /data --console-address :9001`，启动服务并指定容器内数据目录与控制台端口 |
| `environment` | 将 MinIO 账号密码从环境变量传进容器 |
| `ports` | 将容器的 API 和控制台端口映射到本机 |
| 服务内 `volumes` | 把命名卷挂载到容器 `/data` |
| 顶层 `volumes.minio_data` | 声明由 Docker 管理的命名卷 |
| `healthcheck` | 使用 `mc ready local` 检查服务就绪情况 |

`minio_data:/data` 是具名卷，不需要填写 Windows 宿主机路径；如果使用 `./storage/minio:/data`，则属于绑定挂载。容器重新创建后继续使用原卷可以保留数据，删除卷会删除其存储内容。

端口映射为 `127.0.0.1:9000:9000` 与 `127.0.0.1:9001:9001`。Python 使用 9000 的 S3 API，浏览器使用 9001 的控制台。健康检查中使用镜像包含的 `mc` 客户端，避免假设运行镜像一定包含 curl。

### 两类配置的区别

`docker-compose.yml` 决定服务如何启动、如何映射端口；`configs/default.yaml` 记录本机 Python 客户端连接哪些地址。Compose 不会自动读取后者，两处配置需要保持一致。

当前规划的宿主机端口如下，其中后四项目前只是连接配置规划：

| 服务 | 宿主机端口 | 用途 |
| --- | --- | --- |
| MinIO | 9000、9001 | S3 API、控制台 |
| MLflow | 5000 | 实验追踪服务 |
| Airflow | 8083 | 管理页面，计划映射容器 8080 |
| TorchServe | 8080、8081、8082 | 推理、管理、指标 |
| FastAPI | 8000 | 项目 API |

同一电脑上避免宿主机端口冲突；不同容器可以使用相同的内部端口。以后客户端也进入容器时，需要使用服务名和容器端口重新配置连接地址，不能继续把 localhost 理解为宿主机。

```text
silver/m5_v1/m5_processed_full.parquet

```

这里 `silver` 是桶名，`m5_v1/m5_exp_sub.parquet` 是对象名称；斜杠前缀用于组织对象，不是 Windows 文件路径。`m5_v1` 是本次约定的前缀，目前还没有实现自动数据版本管理或版本清单。

### 上传脚本的职责

`ingest_bucket(client, file_path, target_bucket, target_path)` 仅调用 SDK 的 `fput_object()` 并返回上传结果。`main()` 负责读取配置、加载环境变量、创建客户端、拼接本地路径和对象名称，再调用上传函数。

| SDK 参数 | 项目传入值 |
| --- | --- |
| `bucket_name` | 目标桶 |
| `object_name` | 前缀与 `file_path.name` 组成的对象名称 |
| `file_path` | 本地文件路径的字符串形式 |

上传不需要先用 Polars 读取完整文件。创建 `Minio()` 对象也不等于已完成网络连接，实际请求才能验证服务和鉴权是否可用。本次通过真实上传、控制台对象显示和后续集成测试确认链路可用。

当前上传入口一次选择一个文件；今天分别运行完成了全量文件和实验子集的上传，尚未实现批量上传列表或原始 CSV 自动入库。

`tests/test_ingest.py` 的流程为：

1. pytest 的 `tmp_path` 提供临时目录，生成两行数据的 Parquet，包含日期、零销量和空价格。

## 七、今天的排查记录

| 现象 | 原因与修正 |
| --- | --- |
| 用 `sales.get()` 取列或用 `type()` 判断日期列 | 区分 DataFrame、Series、表达式与列 dtype，改用 schema 检查 |
| `schema.get["date"]` | 方法应使用圆括号调用：`schema.get("date")` |
| 用 `with mkdir()` 创建目录 | mkdir 返回 None，直接调用后继续写文件 |
| 拼接输出路径后仍写到 data 根目录 | 文件名被提前拼成绝对路径；改为最后一步才拼文件名 |
| 读取后写 `if not reloader` | DataFrame 不能直接判断真假；通过读取异常和明确的结果检查判断 |
| `sampled_sales.pl.col(...)` | DataFrame 没有该属性；直接取列调用 Series 方法，或在 select 中使用表达式 |
| 单列与列表使用 `not in` | 明确检查不同值数量与集合关系，避免将整列作为单个值比较 |
| 测试表各列长度不一致 | 构建 DataFrame 前确保列长度相同，并按被测函数所接收的长表格式准备数据 |
| 在启动命令中写 curl | command 启动 MinIO，healthcheck 执行就绪检查，两者职责不同 |
| 在上传前读回本地文件就认为验证完成 | 本地读回只验证本地文件；对象存储链路需要实际上传、下载后比较 |

## 八、面试时需要讲清楚的内容

**为什么用小样本？** 本地资源和迭代时间有限，选择可复现的实验范围，保留完整的日历、价格关联和日销量历史，重点验证工程正确性与模型比较。具体商品范围、种子和实际类目组成可以复核。

**为什么先生成全量 Parquet，再独立抽样？** 上下游职责明确；清洗完成的统一产物可被多个实验复用，调整抽样范围不必重新执行原始 CSV 的转换和关联。

**为什么按商品抽样而不是按行抽样？** 预测任务依赖连续历史，按商品选择后保留所有日期，才能构建完整窗口，并让两个门店使用相同商品范围。

**为什么种子固定前还要排序？** 去重和分组的输出顺序可能变化。固定候选顺序与种子，才能在当前库版本下稳定重现选择结果。

**为什么需要 MinIO？** 将数据产物放到统一对象存储入口，为后续调度、训练和服务提供一致的读取位置，并练习本地 S3 兼容数据链路。

**为什么上传测试选择集成测试？** 主要风险在配置、鉴权、服务连接与实际传输；微型文件的真实往返测试可以覆盖这一链路，运行成本也可控。

**当前有哪些限制？** 价格缺失仍保留且原因尚未系统归类；尚未实现时间切分与防泄漏特征；未训练模型；五个应用服务中只有 MinIO 已实际部署。
